# Bait Al Ebdaa mobile app

The Flutter app for iOS and Android. It lives beside the Next.js website in the same repository and never changes it: the website's source files are only read, to build the app's content snapshot.

Architecture and design decisions are in the Phase 1 document: <https://claude.ai/code/artifact/d4ab9465-53cb-451e-be3e-5f49c2c093e6>.

**Status:** launch goes splash → Home, with no sign-in screen. There are five tabs (Home, Services, Projects, Book, Profile), in English and Arabic, all showing real website content. Ask Ali, the assistant, opens from a card on Home. Anyone can browse and fill in a consultation request; sending it needs an account (email sign-in through Firebase Authentication), and the answers are kept while the customer signs in. Sent requests are stored in Cloud Firestore and their status shows under Profile. Ask Ali's backend comes next.

The app is project discovery, consultation requests and request tracking. It is not a shop: there is no cart or checkout, and a request reads "received" until staff schedule it.

## Requirements

- Flutter 3.44.4 (stable) with Dart 3.12.2
- Node 20 or newer, only for `tool/sync_content.mjs`
- Android SDK for Android builds; Xcode on a Mac for iOS builds

## Run

```sh
cd baitalebdaa_app
flutter pub get

# Android (flavors: dev, stg, prod)
flutter run --flavor dev --dart-define-from-file=config/dev.json

# Web preview (no flavors on web)
flutter run -d chrome --dart-define-from-file=config/dev.json
```

A plain `flutter run` (or the IDE's Run button) builds the `dev` flavor, set by `default-flavor` in `pubspec.yaml`. The environment follows the build flavor. A config file that contradicts it (for example, `--flavor prod` with `config/dev.json`) stops the app at launch.

When Firebase starts, every build uses Firebase Authentication and Firestore. When it can't (no network on first launch, or the unregistered `prod` build), `dev` falls back to in-memory fakes so the whole flow still runs, and `stg` and `prod` browse normally while anything that needs the backend offers WhatsApp or phone instead. In `dev`, push and the assistant use stand-ins until their backends exist. A production build with fakes enabled refuses to start.

iOS flavors (schemes and xcconfigs per environment) must be created in Xcode on a Mac. Until then, iOS builds use one scheme with the production bundle ID, and the environment is chosen through `--dart-define-from-file`.

## Firebase

| Build | Firebase project | Status |
| --- | --- | --- |
| dev (`com.baitalebdaa.app.dev`) | `baitalebdaa-76046` | Active: sign-in uses Firebase Authentication |
| stg (`com.baitalebdaa.app.stg`) | `baitalebdaa-76046` | Active |
| prod (`com.baitalebdaa.app`) | `baitalebdaa` | Not registered yet; runs without Firebase |

`lib/firebase_options.dart` and `android/app/google-services.json` were generated by `flutterfire configure` for the production package only. The dev and staging Android apps are not registered yet, so `android/app/build.gradle.kts` has a **temporary** rule that skips the Google Services step for those two flavors. Firebase still starts from `lib/firebase_options.dart`. To register them properly, run from `baitalebdaa_app/`:

```sh
flutterfire configure --project=baitalebdaa-76046 --platforms=android,ios   --android-package-name=com.baitalebdaa.app.dev --ios-bundle-id=com.baitalebdaa.app   --out=lib/firebase_options.dart --android-out=android/app/src/dev/google-services.json --yes
flutterfire configure --project=baitalebdaa-76046 --platforms=android,ios   --android-package-name=com.baitalebdaa.app.stg --ios-bundle-id=com.baitalebdaa.app   --out=lib/firebase_options.dart --android-out=android/app/src/stg/google-services.json --yes
```

Then delete the temporary block in `android/app/build.gradle.kts`. When production goes live, register `com.baitalebdaa.app` in the `baitalebdaa` project, writing to `lib/firebase_options_prod.dart` and `android/app/src/prod/google-services.json`, and point `firebaseOptionsFor(AppFlavor.prod)` in `lib/app/firebase_setup.dart` at it.

Sign-in needs **Authentication → Sign-in method → Email/Password** enabled in the Firebase console. Until it is, the app says email sign-in isn't available.

### Consultation requests (Firestore)

The project is on the free Spark plan, so there is no Cloud Storage and no Cloud Functions. The app writes each request straight to `requests/{id}` in Firestore, and `firebase/firestore.rules` is the only guard: a signed-in customer can create a request (every field checked) and read their own; nobody can change or delete one from the app. Customers share photos and plans on WhatsApp after sending, with the request reference filled in.

Until the rules are deployed, sending fails with a permission error. Deploy them from `baitalebdaa_app/`:

```sh
firebase deploy --only firestore:rules --project baitalebdaa-76046
```

`test/features/request/request_logic_test.dart` checks that the document the app writes matches the field names and allowed values in the rules, so the two cannot drift apart unnoticed. Staff change a request's status in the Firebase console for now.

## Content from the website

Services, prices, projects, reviews, contact details and opening hours all come from the website's own source modules. They are never typed into the app.

```sh
node tool/sync_content.mjs          # regenerate assets/content/content.json
node tool/sync_content.mjs --check  # fail if the snapshot is out of date (CI)
```

Prices are formatted by the website's own `formatPrice()`, so the app shows exactly the website's wording. Only the six owner-confirmed projects (`REAL_PROJECT_SLUGS`) are exported. Run the sync after any change to the website's data and commit the result.

## Checks

```sh
bash tool/ci.sh
```

This runs, in order: the content staleness check, generated-code freshness, `dart format`, `flutter analyze`, `tool/check_conventions.dart`, and the full test suite. The conventions check covers RTL-safe layout and no hard-coded user-facing text. Tests run in both English and Arabic.

Generated code (`*.freezed.dart`, `*.g.dart`, `lib/app/l10n/app_localizations*.dart`) is committed, so a fresh clone runs without a build step. After changing a model or an ARB file:

```sh
dart run build_runner build
flutter gen-l10n
```

## Layout

```text
lib/
  main.dart                 entry point
  app/                      bootstrap, environment, router, root widget, l10n (ARB + generated)
  core/                     failure types, Dio client, platform interfaces (auth, uploads,
                            push, remote settings, analytics, crash), dev fakes, formatting
  design_system/            tokens (colours, type, spacing, motion, icons), theme, components
  features/<feature>/       data / domain / presentation per feature
tool/                       content sync, convention checker, CI script
config/                     non-secret per-environment values (dev, stg, prod)
assets/                     content snapshot, bundled fonts (SIL OFL), licences
```

## Release (Google Play)

The Play package name is `com.baitalebdaa.app` (confirmed 20 Oct 2026). Play never allows it to change.

Release builds are signed with the upload key named in `android/key.properties`. That file is git-ignored, and it points at a keystore kept outside the repository (`C:\Users\Ch Asad Waqas Kamboh\keys\baitalebdaa\upload-keystore.jks`, alias `upload`). Keep a backup of both the keystore and `key.properties` somewhere safe and off this machine. If they are lost, the upload key has to be reset through Play Console support. Without `key.properties`, release builds fall back to debug signing, which Play rejects.

```sh
flutter build appbundle --flavor prod --release --dart-define-from-file=config/prod.json \
  --obfuscate --split-debug-info=build/symbols/prod
```

The bundle is written to `build/app/outputs/bundle/prodRelease/app-prod-release.aab`. Keep `build/symbols/prod` for each release, because it is needed to read crash stack traces. Raise `version:` in `pubspec.yaml` before every upload; the number after `+` is the Play version code.

The store listing icon is `store/play_icon_512.png`. Launcher icons for Android, iOS and web are generated from `assets/brand/icon/` with `dart run flutter_launcher_icons` (settings in `pubspec.yaml`).

Enrol in Play App Signing when creating the app. Google then holds the app signing key, and this keystore is only the upload key.
